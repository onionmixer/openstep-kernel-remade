# Kernel reconstruction requirements

- User requirement: use Python for all explicit calculations (including address/offset conversion, sizes, counts, differences, percentages and coverage aggregation). Do not perform these mentally or with shell/JavaScript arithmetic. Preserve analysis-tool outputs as evidence and use Python to calculate derived results.

- Current user-directed scope (2026-10-01): the 2026-09-13 analysis-only restriction is withdrawn. Source reconstruction, building and testing of the kernel are authorized; follow `02_plan/RECONSTRUCTION_PLAN.md`. Reference code in `01_resources` (Mach4, NeXTMach, Darwin 0.1) may be consulted, but a reference text is a candidate, not a fact about the original: adopt it only with evidence checked against the original kernel bytes, and record source, revision and license per file and per function (`07_kernel/PROVENANCE.tsv`, `06_reconstruction/`).
- NeXTMach-derived code may be committed to the public repository (user decision D013, 2026-10-01; license judgement is the user's): record its origin (repository URL, commit, path:line) and keep its original notices, per file, function or identifier, in `07_kernel/PROVENANCE.tsv` and `07_kernel/MODIFICATIONS.md`. Darwin 0.1 (APSL) and Mach4 text is committed only with its license notice and provenance entry. Exception (user decision D030, 2026-10-04): a Darwin-only file outside Darwin kernel/machdep with no Mach4/NeXTMach counterpart (driverkit/libDriver files, bsd/dev/ev.c and the like) stays project-authored (D027) without Darwin's notices even when its text is nearly Darwin's; its file head, `07_kernel/PROVENANCE.tsv` and `07_kernel/MODIFICATIONS.md` must say "nearly the same as Darwin 0.1 <file>".
- Workflow: write the plan first, cross-check it with codex (MCP) before coding, and verify every codex claim independently; codex output is never evidence by itself.
- Build and test: i386 kernels are built on the OPENSTEP real machine (the repository is NFS-mounted there at `/ndrv/openstep-kernel-remade`; commands go through `gcds`) and tested in the QEMU VMs (`11_emulation/`). Rebooting, replacing the kernel on, or restarting daemons of the real machine is done by the user; site addresses and accounts stay out of committed files.

- The reconstructed kernel must compile with GCC 2.7, including later architecture targets. The toolchain candidate is NeXT `cc-744.13` (GCC 2.7.2.1 based) installed in the i386 and m68k VMs; it counts as verified only after the probes in `08_build/GCC27_COMPATIBILITY.md` pass with it.
- Follow `08_build/GCC27_COMPATIBILITY.md` for source, generated code, ABI and acceptance criteria.
- Use C89-style source as the baseline. GNU/NeXT extensions require evidence from the selected GCC 2.7 toolchain.
- Do not mark compiler compatibility verified using only a modern compiler or a language-standard flag.
- Preserve reference inputs in `01_resources` and original binaries in `03_original`; edit reconstructed code in `07_kernel`.
- Keep original binary facts, decompiler interpretations, reconstructed implementations and validation results separate.

- Emulator platform (2026-09-30 user direction): `11_emulation/` holds the qemu-NeXT source with an uncommitted lab diff, its out-of-tree build, firmware and launch scripts; follow `11_emulation/README.md` (no checkout/reset/stash/clean in `qemu-NeXT/`, no configure inside it). Building and booting reconstructed kernels there follows `02_plan/RECONSTRUCTION_PLAN.md`; always boot a new kernel with `--snapshot` first. `12_archive/` holds imported records of other workspaces; they are not evidence for the original kernel.
