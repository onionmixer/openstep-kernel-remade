# x86 분석의 신중한 추가검토

검토일: 2026-09-11. 대상: OPENSTEP 4.2 mk-183.34.4 / i386.
원본 SHA-256: `33469393c0843fc741942c3ae9d91d838467d72abd647dcf2e5bf499a3f14890`.
선행 보고서: [상세 재검토](../deep-review-20260911/README.md).

## 결론

기존의 **“자료 확보와 의미적으로 정확한 분석 완료는 다르다”는 판정을 유지**한다.
이번에는 예외 복귀의 잘못된 fallthrough와 `_jump_label` 인자 해석 문제를 추가 확인했다.
반대로 panic 뒤 코드와 CPU 초기화의 특정 HLT 경로는 단순히 C에 없다는 이유로
실행 기능 누락이라고 판정하면 안 된다는 근거를 강화했다.

이번 검토 범위에서 원본 또는 기존 export의 새 파일 누락·변조는 발견하지 않았다.
그러나 fault recovery의 문맥 연결, 예외 복귀 계약, 타입과 함수 경계는 여전히 보완 대상이다.
GCC 2.7 구현·컴파일·부팅 검증을 완료했다는 의미가 아니다.

원본, 기존 export, Ghidra/IDA DB는 수정하지 않았다. 이 디렉터리에 검토 자료만 추가했다.
Ghidra·IDA 스킬의 분석 자료와 원본 사실 분리 원칙에 따라 저장된 출력과 원본 바이트를 대조했다.
이전 읽기 전용 Ghidra 추출물을 사용했으며 이번에 라이브 DB를 다시 분석하거나 저장하지 않았다.
모든 주소·오프셋 계산, 비트 연산, 집계, 테스트 및 해시 검증은 Python으로 수행했다.

## 추가 확인 결과

### F01 — 예외 복귀를 일반 함수 반환으로 표시하는 문제가 호출자에 전파됨

확신도: 높음. 실제 원본 제어 이동과 C 출력의 불일치.

`__return_with_state` (`0x00186f04`)는 현재 CALL 복귀 주소를 POP하여 버리고,
상태 프레임으로 ESP를 바꾼 뒤 세그먼트·범용 레지스터를 복원하고 `0x00186f1e`에서 IRETD한다.
현재 호출자의 다음 명령으로 일반 RET하는 함수가 아니다.

이 함수로 끝나는 `_thread_exception_return`과 `_thread_syscall_return`에도
물리적인 후속 에필로그는 있지만, 정상적인 이 경로에서 그 에필로그로 돌아오지 않는다.
저장된 Ghidra 정보에는 이 세 함수 모두 `noreturn: false`로 되어 있다.
이 플래그만으로 오류를 단정한 것이 아니라 원본 명령과 호출자 C를 함께 확인했다.

대표적인 실제 영향은 `_machdep_call` (`0x001925a0`)이다.

- 잘못된 호출 번호 경로에서 `_kern_invalid`의 결과를 저장하고 `0x001925f6`에서
  `_thread_exception_return`을 호출한다.
- C 출력은 이 호출 뒤에도 호출 번호를 사용한 테이블 접근이 이어지는 형태다.
- 원본의 정상적인 예외 복귀 의미에서는 그 지점으로 fallthrough하지 않는다.
- 따라서 C 출력만 보고 실제 커널의 범위 밖 테이블 접근 취약점이라고 결론 내리면 안 된다.

전체 인식 instruction에서 `_thread_exception_return` 직접 호출은 **21곳, 소유 분석 단위 16개**다.
이것은 영향 검토 목록이지, 서로 독립적인 확정 오류 21건이라는 뜻은 아니다.
`__return_with_state` 직접 호출은 `_thread_exception_return`의 `0x0018df6f`와
`_thread_syscall_return`의 `0x0018e03f`다.

근거: Ghidra 최종 export의 `functions/00186f04.asm`, `0018dec0.asm`, `0018df80.asm`,
`001925a0.c`, `001920f4.c`; [호출 목록과 플래그](recovery-and-return-inventory.json).

### F02 — fault recovery 주소는 확보되어 있지만 일반 CALL/JMP 관계로는 연결되지 않음

확신도: 소비 경로와 직접 확인된 저장 경로는 높음. 나머지 후보의 기반 포인터 출처는 미확정.

`FUN_001924a0`은 `_active_threads`에서 현재 thread 포인터를 읽고 해당 구조의 `+0x74` 값을 읽는다.
값이 있으면 전달받은 프레임 포인터 기준 `+4`에 복구 주소를, `+8`의 하위 word에 CS 값 8을 저장한다.
`+0xc`의 플래그에서 `0x400` 비트를 지우고 thread의 복구 주소를 0으로 만든 뒤 1을 반환한다.
복구 주소가 처음부터 0이면 프레임을 변경하지 않고 0을 반환한다.

호출자 `_kernel_trap`은 원래 프레임에 `0x34`를 더한 포인터를 전달한다.
따라서 원래 프레임 기준 쓰기 위치는 Python 계산으로 EIP `0x38`, CS `0x3c`, EFLAGS `0x40`이다.
즉, 복구 지점은 일반 함수 호출이 아니라 예외 프레임의 복귀 주소 변경을 통해 선택된다.

원본 명령을 재해석하여 `[기반 레지스터 + 0x74]`에 코드 주소 즉시값을 저장하는 패턴을 검사했다.

| 검사 | 결과 | 해석 |
|---|---:|---|
| 후보 저장 명령 / 고유 목적지 | 50 / 50 | 이 특정 패턴에 대한 결과, 모든 복구 경로의 전수 목록은 아님 |
| 기존 fragment 진입점과 일치하는 목적지 | 50 | 검사한 목적지의 assembly 자료가 없는 것은 아님 |
| 소유 본문 내부지만 진입점은 아닌 목적지 | 0 | 현재 인벤토리 기준 |
| 바로 앞 명령의 `_active_threads` 로드로 기반 포인터 출처 확인 | 14 | copyin/out·문자열·사용자 메모리 접근 함수군 |

14개 직접 확인 사례는 `_copyin`, `_copyinmsg`, `_copywithin`, `_copyout`, `_copyoutmsg`,

나머지 후보도 같은 오프셋이라는 이유만으로 모두 thread 복구 필드라고 확정하지 않았다.
로컬 Darwin `kernel/machdep/i386/fault_copy.c`의 `current_thread()->recover`와 label-address 사용은
계보를 뒷받침하지만 대상 OPENSTEP 바이너리의 구조체 전체 동일성을 증명하지 않는다.

보완 대상은 복구 지점의 파일 재수집보다는 원래 함수의 스택·세그먼트·오류 반환과 연결한 검증이다.
검사 패턴에 잡히지 않는 간접 저장이나 계산된 복구 주소가 없다고 주장하지 않는다.

근거: `functions/001924a0.asm`, `001920f4.asm`; [저장 명령의 주변 문맥](supplementary-checks.json).

### F03 — `_jump_label`의 두 번째 인자를 복원된 ABI로 채택하면 안 됨

확신도: 직접 읽는 인자와 마지막 EAX 값은 높음. 전체 실행은 아래 외부 호출 가정을 따른다.

`_jump_label` (`0x00186fb0`)은 진입 스택의 첫 번째 인자만 직접 읽어 저장 문맥 포인터로 사용한다.
이 문맥에서 EDI/ESI/EBX/EBP/ESP와 복귀 주소를 복원하고 `_splx`를 호출한 뒤 EAX에 1을 넣고 RET한다.
두 번째 인자를 읽어 반환값으로 사용하는 명령은 없다.

그런데 Ghidra C는 두 인자의 함수로 표시하며 `_sleep`, `_sleep_with_continuation`,
`_sleep_with_continuation_and_deadline`에서 `unaff_EBX`를 두 번째 인자처럼 출력한다.
해당 호출 직전 원본에는 문맥 포인터를 인자로 PUSH하는 명령이 있다.
따라서 이 `unaff_EBX`를 실제로 필요한 두 번째 인자로 복원할 근거는 없다.
`_NXDefaultExceptionRaiser`는 추가 값도 PUSH하지만 이 callee가 그 값을 사용하는 것은 아니다.

선행 R01의 이웃 함수 혼입 판정은 유지한다. IDA의 `longjmp` 표현은 비지역 이동을 이해하는 데
도움이 되지만 표준 C `longjmp(env, value)`의 반환값 규약까지 동일하다는 증거로 쓰면 안 된다.

근거: `functions/00186fb0.asm`, `0010a588.c`, `0010a708.c`, `0010a898.c`, `001cad48.asm`;
[제한된 상태 전이 테스트](bounded-state-tests.json).

### F04 — panic 뒤 코드의 생략과 문맥 전환을 구분해야 함

확신도: 정상적인 호출/복귀 및 제어 흐름을 전제로 한 구조적 근거.

`_panic`에는 파일상 RET가 있지만 `0x0010cb16`에서 첫 인자 0으로 `_boot`를 호출한다.
`_boot`는 `_md_do_shutdown`을 호출하며, 이 함수의 확보된 본문에는 RET 명령이 없고
HLT/JMP 자기 루프가 `0x0018d08c`, `0x0018d140`, `0x0018d1c8`에 있다.
종료 호출들이 정상적으로 반환하는 경우에도 현재 호출자에게 돌아가는 에필로그로 이어지지 않는다.
디버거의 강제 PC 변경이나 임의 문맥 변경까지 배제한 하드웨어 증명은 아니다.

따라서 선행 보고서의 panic 뒤 synthetic fragment 생성 기록 418개를
“실제 실행되는 코드 418곳의 디컴파일 누락”으로 해석하지 않는다.
이번 전체 직접 `_panic` 호출 집계 481곳은 다른 모집단이며 418과 불일치하는 오류가 아니다.
이 종료 경로는 ObjC 오류 경로의 정상 비복귀 해석과 선행 R02 판정도 뒷받침한다.

반면 `__switch_tss`는 기존 문맥이 주어진 경로에서 현재 복귀 주소와 ESP를 저장하고
다른 문맥의 주소로 JMP한다. 이후 기존 문맥이 다시 선택되면 저장된 호출 후속 지점으로
실행이 재개될 수 있다. 모든 간접 JMP 함수를 일괄 `noreturn`으로 바꾸면 이 관계를 잃을 수 있다.
`__call_with_stack`도 별도의 스택 인계 계약으로 다뤄야 한다.
이번 검토에서는 어떤 함수의 플래그도 변경하지 않았다.

근거: `functions/0010ca6c.asm`, `00108b84.asm`, `0018cfc8.asm`, `00186f20.asm`, `00186f7c.asm`.

### F05 — CPU 초기화의 첫 HLT 경로와 CPUID 조건을 혼동하지 않음

`FUN_0018ac28`의 `0x0018ac33`은 EDX에 `0x40000`을 OR하고,
`0x0018ac3b`는 변경되지 않은 같은 EDX에 같은 마스크를 TEST한다.
Python으로 검사한 해당 비트의 초기값 양쪽 경우 모두 TEST 결과는 `0x40000`이다.
정상적인 순차 실행에서 `0x0018ac41`의 JZ가 HLT로 향하지 않는다는 선행 판정을 유지한다.

이는 뒤쪽의 CPUID 가능 여부 판정과 다르다. 뒤쪽에는 POPFD 이후 PUSHFD/POP으로
플래그를 다시 읽는 코드와 조건 분기가 있다. CR0/WBINVD 및 이 조건의 C 표현 부족이라는
선행 R03 문제는 여전히 남아 있다. CPU 명령을 실제 실행하여 검증하지는 않았다.

## Python 검사 결과와 한계

- 복구 프레임 helper: 복구 주소와 플래그를 조합한 12개 제한된 상태 전이 테스트 통과.
- `_jump_label`: 저장 목적지와 두 번째 인자를 조합한 9개 제한된 테스트 통과.
- 기존 최종 export 해시: 15,770개 재검증, 불일치 없음.
- 선행 상세검토 자료 해시: 12개 재검증, 불일치 없음.
- 원본 SHA-256: 기준값과 일치.

테스트는 원본 바이트를 Capstone으로 decode한 뒤 필요한 일부 명령만 해석하는 Python 모델이다.
알 수 없는 명령은 실패하도록 했으며 전체 x86 에뮬레이터가 아니다.
특히 `_jump_label` 모델의 `_splx`는 정상 반환과 보존 레지스터·저장 목적지 유지로 대체했다.
실제 `_splx`에는 CLI/STI, 포트 I/O, `0x0018b59b`의 간접 callback 호출이 있으므로
이 모델은 그 하드웨어·callback 동작을 검증한 것이 아니다.
테스트 통과를 전체 입력 증명, 커널 부팅 성공 또는 GCC 2.7 호환성 확인으로 확대 해석하지 않는다.

재현: 프로젝트 루트에서 `python3 09_validation/reports/cautious-followup-20260911/review.py`.
Python 3와 현재 환경의 `capstone` 모듈을 사용하며 기존 분석 파일은 읽기만 한다.

## 다음 분석 단계의 통과 조건 — 아직 수행하지 않음

1. 예외 복귀·비지역 이동·다시 재개 가능한 문맥 전환을 서로 다른 계약으로 명세한다.
2. fault recovery 후보의 기반 포인터 출처를 추적하고 원래 함수의 실패 경로와 결합한다.
3. 별도 작업 DB에서 근거 있는 경계·타입·복귀 계약을 적용하고 전후 결과를 비교한다.
4. R01 이웃 함수 혼입, R02 정렬 바이트 오인, F01 잘못된 fallthrough가 제거됐는지 확인한다.
5. IDA containing function·입력 바이트 검증, CPU/ObjC ABI 및 callback 분류의 미해결 항목을 닫는다.
6. 이후 GCC 2.7용 C/assembly 구현과 실제 toolchain·부팅 검증을 별도 단계로 수행한다.

현재 판정: **추가검토 완료. 분석 전체의 의미적 정확성과 누락 없음은 미확정.**
