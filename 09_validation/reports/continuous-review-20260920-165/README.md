# `_vm_map_deallocate` 잠금·참조수명 순서

Open item 2의 `deallocate` 잠금 및 수명 경계를 원본 x86 바이트에서 확인했다.
분석 도구의 `_vm_map_deallocate` 명칭은 위치를 찾는 가설로만 사용했고, 결론은
`0x001747d8`부터 `0x00174845`까지의 원시 명령어에 한정한다.

입력 포인터가 0이면 바로 반환한다. 그렇지 않으면 `+0x34` 주소를 만든 뒤, 값이 0일
때까지 읽고 `1`을 `XCHG`한다. 교환에서 얻은 이전 값은 `XOR EAX,1`과 `TEST`를 거쳐
0이면 다시 시도한다. 성공 뒤에는 `+0x30`의 이전 값을 읽어 `이전값 - 1`을 저장하고,
`EAX`도 감소시킨 다음 `+0x34`를 0과 `XCHG`한다.

감소한 값이 양수이면 즉시 반환한다. 양수가 아닌 경로에서만 원시 direct `CALL` 네 개가
차례로 나타난다: `0x0015b5d0`, `0x00176164`, `0x0018f69c`, `0x0016b84c`.
두 번째 호출 전에는 같은 객체와 `+0x14`, `+0x18`의 읽은 값을 push하고, 세 번째 전에는
`+0x24` 값을 push한다. 첫 호출 뒤에는 `+0x4c`를 1 증가시킨다. 네 번째 호출 뒤에는
반환 전 `EAX`를 명시적으로 쓰지 않는다.

이는 잠금처럼 보이는 `+0x34` 보호 구간이 `+0x30` 감소까지만 바이트상 분명하다는
증거다. `+0x34`의 실제 자료형, 호출 대상의 의미, 해제 완료 시점, 호출 실패 시의 롤백,
그리고 호출 전후 상위 잠금 보유 여부는 이 범위만으로 확정하지 않는다. 159차의 direct
caller EAX 경계도 이 callee 내부 호출의 반환 의미나 간접 caller를 판정하지 않는다.
