# 연속 추가검토 — lock 대기와 획득 재시도의 표현 손실

대상: OPENSTEP 4.2 mk-183.34.4 / x86. 검토일: 2026-09-11.
원본 SHA-256: `33469393c0843fc741942c3ae9d91d838467d72abd647dcf2e5bf499a3f14890`.
출발점: [이전 API 검토의 미해결 lock 항목](../continuous-review-20260911-10/README.md).

## 결론

현재 발견된 명령 전체를 원본 바이트로 다시 디코딩해 짧은 대기 역분기를 분류했다.
403개 함수 단위에 걸친 901곳은 lock 값을 한 번 읽고 레지스터만 반복 검사한다.
같은 짧은 역분기 패턴 중 3곳은 메모리를 매번 다시 읽는다.
이 차이는 디컴파일러가 만들어 낸 것이 아니라 현재 원본 명령에 존재한다.

별도로, 일부 전역 lock에서는 실제 XCHG 결과에 따른 재시도 분기가
Ghidra의 최적화된 P-code 및 C 출력에서 사라지는 것을 확인했다.
표현상 `while (*lock)`이 보이거나 `LOCK()/UNLOCK()`이 남아 있는 것만으로
원본 동기화 의미가 온전히 보존됐다고 판정할 수 없다.

대기 구간 전수 제한 실행은 5,421개 조건에서 통과했다.
실제 XCHG·재시도까지 포함한 추가 경쟁 모형 시험은 16개 조건에서 통과했다.
이는 합성 메모리·외부 쓰기 조건에서 원본 구간의 동작을 확인한 것이다.
실제 SMP, interrupt, scheduler, 하드웨어 또는 부팅의 동시성 검증은 아니다.
전체 분석 완료 및 실제 시스템 교착으로 단정하지 않는다.

## 원본의 두 가지 대기 형태

[전수 분류 결과](scan.json), [Python 디코딩·분류 코드](scan.py).

`_thread_policy`의 해당 원본은 다음과 같다.

```asm
00168937  8b0a  mov  ecx, [edx]
00168939  85c9  test ecx, ecx
0016893b  75fc  jne  00168939
```

역분기의 목적지는 `MOV`가 아니라 `TEST`다.
한 번 읽은 ECX가 0이 아니면, 이 구간 자체는 이후 lock 메모리 변경을 관찰하지 않는다.
TEST는 일반 레지스터를 바꾸지 않고 분기에 사용할 flags만 갱신한다.
따라서 외부에서 메모리만 변경하고 레지스터·실행 흐름을 바꾸지 않는 조건에서는
같은 분기가 유지된다. 이는 제한 횟수 시험만 보고 무한 반복을 추측한 것이 아니라
명령의 읽기·쓰기 집합과 분기 대상으로 확인한 불변 조건이다.

대조군 `FUN_001ca960`은 다음과 같다.

```asm
001ca968  833d34551e0000  cmp dword ptr [001e5534], 0
001ca96f  75f7            jne 001ca968
```

이 구간은 CMP가 메모리를 읽기 때문에 다음 반복에서 외부 변경을 관찰한다.

| 분류 | 지점 수 | 의미 |
|---|---:|---|
| 레지스터 TEST로 되돌아감 | 901 | 대기 반복 자체에는 메모리 재읽기 없음 |
| 메모리 CMP로 되돌아감 | 3 | 반복마다 메모리 읽기 |
| 이 정확한 패턴의 합계 | 904 | 406개 함수 단위에 분포 |

레지스터형 모두 선행 단일 메모리 LOAD와 대응한다.
그중 8곳은 LOAD와 TEST 사이에 NOP가 있어, 바로 앞 명령만 보는 최초 분류에서는
대응을 찾지 못했다. NOP를 건너뛰어 원본 LOAD까지 확인했고 미분류로 숨기지 않았다.
901곳 모두 뒤쪽 제한 명령 창에 XCHG가 있다.
`nearby_exchange`는 가까운 XCHG 존재를 뜻하며, 전수 alias·lock 소유권 증명은 아니다.

분류 범위는 현재 export된 5,253개 함수 단위의 고유 instruction head 286,091개다.
조건은 **바로 앞 TEST/CMP로 되돌아가는 JNE**로 고정했다.
다른 조건 분기, 더 긴 loop, MMIO, 간접 분기 및 아직 발견되지 않은 코드를 모두
조사했다는 뜻은 아니다. 이 수치를 전체 커널의 모든 lock 개수로 사용하면 안 된다.

## Ghidra의 어느 단계까지 보존되는가

[추출 프로그램](WaitPcodeEvidence.java), [실행기](extract_pcode.py),
[raw/high P-code](exports/pcode.json), [비교 결과](pcode-audit.json),
[비교 코드](audit_pcode.py).

검토한 함수는 `_panic`, `_mfs_cache_trim`, `_task_create`, `_thread_policy`,
`FUN_001ca960`, `_NXAllocErrorData`, `FUN_001cbc80`이다.
해당 함수의 이번 C 출력은 정본 full-pass5와 동일하다.
새 복제 프로젝트에서 읽기 전용으로 추출했으며 타입·함수·명령을 수정하지 않았다.

### 레지스터 대기: C의 표면적 모양과 실제 읽기 위치를 구분해야 한다

`_thread_policy`의 high P-code는 다음 관계를 보존한다.

- LOAD `00168937`은 선행 block에 있다.
- 대기 block `00168939`에는 비교와 자기 자신으로 향하는 조건 분기만 있다.
- 대기 block에는 LOAD가 없다.

그런데 C 출력은 `do { } while (*piVar1 != 0);`로 읽힌다.
여기서 포인터가 volatile로 표시되지 않았다는 점도 중요하다.
이를 반드시 매 반복마다 메모리를 읽는 코드로 해석하거나,
그 모양만으로 Ghidra가 잘못된 기계 동작을 만들었다고 단정하지 않았다.
현재 확인된 사실은 raw 명령과 이 함수의 high P-code에 단일 읽기가 보존된다는 것이다.

로컬 Darwin 참고 소스 `mach/i386/simple_lock.h`도 `while (slock->locked)`와
`simple_lock_try`의 XCHG를 조합한다. 해당 필드는 `boolean_t locked`이고,
i386 `boolean_t`는 `unsigned int`이며 volatile 한정이 없다.
이 소스 형태는 단일 읽기 코드와 양립할 가능성을 보여 주는 참고 근거다.
그 파일이 현재 바이너리의 정확한 소스였다거나 특정 GCC 버전이 이 코드를 생성했다는
증명은 아니다. 실제 GCC 2.7 툴체인으로 해당 코드 생성을 재현하지 않았다.

### 전역 lock: 재시도 분기와 일부 대기 자체가 최적화 결과에서 사라짐

선택 함수 내 9개 대기 지점 모두 원본과 raw P-code에는 대기 및 획득 재시도 분기가 있다.
그러나 high P-code에서는 다음 획득 재시도 분기가 남지 않았다.

| 함수 | 원본 재시도 분기 |
|---|---|
| `_panic` | `0010ca91` |
| `_mfs_cache_trim` | `0015ec24`, `0015ecb1` |
| `FUN_001ca960` | `001ca981` |
| `_NXAllocErrorData` | `001cae51` |

또한 `_mfs_cache_trim`의 두 번째 대기 분기 `0015ec9f`도 high P-code에서 사라졌다.
원본은 unlock XCHG 이후 값을 다시 읽고 재획득을 시도하지만,
현재 C에는 그 사이에 빈 `LOCK(); UNLOCK();` 쌍만 남는 부분이 있다.

이것은 원본에 재시도 코드가 없다는 뜻이 아니다.
비동기 메모리 변경을 정확히 모델링하지 않은 최적화 결과를
커널 동기화 소스로 그대로 채택하면 필요한 동작을 잃는다는 구체적 위험이다.
이번에는 데이터에 volatile을 일괄 적용하거나 분석 DB를 교정하지 않았다.
어떤 memory/atomic 모델을 적용해야 원본에 맞는지는 후속 실험 대상이다.

high P-code의 주소 구간만으로 operation 소속을 판단하지도 않았다.
최적화된 block은 비연속 원본 위치를 합칠 수 있으므로,
비교 스크립트는 실제 operation의 주소와 opcode로 분기 잔존 여부를 검사한다.
전역 메모리가 `ram` varnode/COPY로 표현될 수 있어 LOAD opcode 개수만으로
모든 메모리 읽기 수를 세는 접근 역시 사용하지 않았다.

## 원본 실행 시험

### 전체 대기 창

[시험 코드](wait_execution.py), [전체 조건과 trace](wait-execution.json).

901개 레지스터형과 3개 메모리형 지점 모두를 실행했다.
원본 instruction을 패치하지 않고 메모리·레지스터 fixture만 설정했다.

검사한 조건:

- 처음부터 0인 경우.
- 0이 아닌 값이 계속 유지되는 경우.
- 최초 읽기 전에 합성 외부 해제가 일어난 경우.
- 최초 읽기 후 합성 외부 해제가 일어난 경우; 서로 다른 비영 값 사용.
- 레지스터형은 메모리 대신 검사 레지스터를 인위적으로 0으로 만드는 대조 조건.

읽기 후 메모리를 해제한 레지스터형 1,802개 조건은 대기를 벗어나지 않았다.
해당 창에서 메모리 읽기는 각각 한 번이었다.
메모리형의 대응 6개 조건은 두 번째 읽기에서 0을 보고 대기를 벗어났다.
계속 대기하는 조건은 instruction 상한에 도달하면 중단했다.
레지스터 강제 변경은 민감도 대조 시험이며 정상 unlock이나 interrupt 동작을 뜻하지 않는다.

### 실제 XCHG와 획득 경쟁

[추가 시험 코드](contention_execution.py), [추가 결과](contention-execution.json).

`_panic`, `_mfs_cache_trim`, `FUN_001ca960`, `_NXAllocErrorData`의
각 선택 구간에서 실제 XCHG와 재시도 분기까지 실행했다.
처음 확인한 lock 값은 0이지만 XCHG 직전에 합성 경쟁자가 1을 쓰도록 했다.

원본은 XCHG가 돌려준 이전 값에 따라 실제 재시도한다.
재읽기 전에 해제하면 재획득할 수 있지만, 재읽기 후 해제하면
레지스터형은 읽어 둔 비영 값에 머물고 메모리형은 다음 읽기에서 해제를 관찰한다.
이 시험은 C에서 사라진 재시도 경로가 원본에서는 실행될 수 있음을 보여 준다.
경쟁자 쓰기는 Python hook으로 지정한 사건이며 실제 별도 CPU를 실행한 것은 아니다.

## 복원에 미치는 영향과 남은 작업

- 일반 C의 `while (*lock)` 표기만으로 정확한 읽기 횟수·동기화 의미를 결정하지 않는다.
- 원본에서 확인한 단일 읽기 동작과, 운영 환경에서 기대하는 동시성 동작을 구분한다.
- 원본과 다른 `volatile` 재읽기를 무조건 추가하거나, 원본의 재시도를 삭제하면 안 된다.
- XCHG의 이전 값, 획득 재시도, unlock 기록 및 memory ordering을 별도 계약으로 검증해야 한다.
- 특정 실행 경로에서 lock이 실제로 비영 값으로 관찰 가능한지, 단일 CPU·interrupt 규약으로
  경쟁이 배제되는지, 이 이미지의 배포·패치 이력이 무엇인지는 이번 시험으로 확정하지 못했다.
- 다른 형태의 대기 루프, atomics 및 barrier의 high P-code/C 손실도 추가 조사해야 한다.
- 데이터 volatile/atomic 모델에 따른 격리 실험, GCC 2.7 코드 생성 및 실제 커널 실행 검증은 남아 있다.

이번 검토는 Ghidra 스킬에 따라 원본 listing, 함수, raw/high P-code를 단계별로 대조했다.
원본 바이너리·정본 분석 DB·기존 보고서·`07_kernel`은 수정하지 않았다.
모든 수치 계산·주소 변환·집계·해시·실행 모형은 Python으로 처리했다.
